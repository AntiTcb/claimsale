# Tech Stack — Proposal and Open Questions

Versions are the latest on npm as of **2026-10-08**. Status: **proposed**. Each
question below has a recommended default in *italics*. Once answered, this
becomes the decision record for the stack.

---

## 1. A constraint that shapes the layout

`@sveltejs/adapter-cloudflare@8` generates the Worker entry file itself, and that
file exports **only a `fetch` handler**. If `wrangler.main` is set, the adapter
writes its output *to that path*, so you can't point it at a hand-written entry.

We need three more handlers: Durable Object classes (the sale engine), a **Queue
consumer** (notifications), and a **`scheduled`** handler (the cron sweep). Also,
`vite dev` reaches bindings through `getPlatformProxy`, which can only talk to a
Durable Object that lives in *another* Worker (`script_name`).

**Proposal: two Workers in a pnpm monorepo.**

```
apps/
  web/        SvelteKit 3 app → Worker "claimsale-web" (adapter-cloudflare)
              binds: D1, R2, KV?, Queue producer, SALE_ENGINE (DO, script_name=claimsale-engine),
                     ENGINE (service binding, RPC)
  engine/     plain Worker "claimsale-engine"
              exports: SaleEngine (Durable Object), queue() consumer, scheduled() sweep
              binds: D1, Queue, email/SMS secrets
packages/
  core/       pure TypeScript: state machines, ranking, money, entitlements, reason codes
              (no I/O; unit- and property-tested)
  db/         Drizzle schema, migrations, typed queries shared by both Workers
  emails/     email templates
```

- In development, `wrangler dev` runs the engine and `vite dev` runs the web app;
  the web app reaches the engine's DO through wrangler's local dev registry.
- In production, both deploy from CI. The web app calls the engine via **RPC over
  a service binding** (`env.ENGINE.placeEntry(...)`) and opens WebSockets by forwarding
  to the DO stub.

## 3. Questions

### Architecture
- **T1. Worker layout.** Two Workers in a pnpm monorepo (section 1), *or* a single
  Worker built by wrapping the adapter's output in a custom entry after the build
  (fewer moving parts in production, but a brittle build and weaker local dev)?
  *Two Workers + monorepo.*
- **T2. Remote functions.** SvelteKit's `query` / `form` / `command` remote
  functions are still **experimental** in 3.0.1 (`kit.experimental.remoteFunctions`).
  - (a) Use them anyway: they're the direction SvelteKit is going, and they fit
    this app well, but they may break between minor versions.
  - (b) Use classic `load` + form actions + `sveltekit-superforms` (3.0.0): stable,
    but more boilerplate.
  - *(a) for new code, wrapped in a thin layer so a breaking change only touches
    one place.*
- **T3. Engine RPC.** Should the web app call the engine through typed **Workers RPC**
  (`WorkerEntrypoint` methods), or through plain `fetch` + JSON routes? *RPC.*

### Data
- **T4. Validation library.**
  - Valibot: modular, with small client bundles.
  - Zod 4: bigger ecosystem and more familiar; `zod/mini` exists if size matters.
  - *Valibot.* Validation schemas are shared by client forms and server
    commands, so bundle size matters.
- **T5. ORM.** Drizzle (schema-first, migrations, D1 driver) or Kysely (a pure query
  builder; you write the migrations)? *Drizzle.*
- **T6. Search.** D1's built-in **FTS5** full-text search, or an external engine
  (Typesense / Meilisearch / Algolia) for typo tolerance and facets? *FTS5 at launch.
  Card names will need some typo handling; card-name autocomplete runs against the
  YGOPRODeck cache table instead.*
- **T7. Environments.** Local, **per-PR preview**, staging and production, each with
  its own D1 and R2? Or skip staging? *Local + PR previews (sharing a preview D1)
  + production. Add staging when someone else is using it.*

### Auth and identity
- **T8. Auth library.** Better Auth (batteries included: magic link, OTP, OAuth, sessions
  in D1), Auth.js (`@auth/sveltekit`, which has weaker phone/OTP support), or a
  hand-rolled session system following the Lucia guide? *Better Auth.*
- **T9. Sign-in methods at launch.** Options: email magic link, Google, **Discord**
  (the YGO community lives there), Facebook (no profile link without app review),
  Apple, passkeys.
  - *Magic link + Google + Discord + passkeys. Add Facebook when you need it
    for FB group integrations.*
- **T10. Phone verification provider.** Twilio Verify (about $0.05 per check, with
  built-in fraud guard), Prelude, or Telnyx? Should we also **reject VoIP / prepaid
  numbers** using a line-type lookup, to stop one person verifying many seller
  accounts?
  - *Twilio Verify, with VoIP numbers rejected.*

### Front end
- **T11. UI kit.** shadcn-svelte (owned copies on bits-ui, Tailwind v4), Skeleton,
  DaisyUI, or fully custom? Light and dark mode? *shadcn-svelte, both themes
  following the system setting.*
- **T12. Text formatting** in sale and item descriptions and messages:
  - plain text with auto-linked URLs,
  - limited Markdown (bold, italic, lists, links), or
  - a rich-text editor (Tiptap).
  - *Limited Markdown for descriptions; plain text for messages.*
- **T13. Share images (OG cards).** `workers-og` is quick, but it's a small,
  pre-1.0 project. `satori` + `resvg-wasm` is more control and more setup. Or a
  static per-sale cover image with text overlay done in CSS via a prerendered route.
  *satori + resvg-wasm, cached in R2 per sale version.*
- **T14. PWA.** Make the site installable (needed for **web push on iOS**) with a
  hand-written service worker, or use `@vite-pwa/sveltekit`? *Hand-written, small:
  a manifest plus push handling only, no offline caching at first.*
- **T15. Client-side image processing.** Hand-written resizing with
  `createImageBitmap` + `OffscreenCanvas` (no dependency), or `browser-image-compression`?
  Output format WebP or JPEG? *Hand-written; WebP at 0.85 quality, max 2000px.*

### Operations
- **T16. Error tracking and analytics.**
  - Sentry (errors + performance), or rely on Workers Logs + Logpush only?
  - Product analytics: Cloudflare Web Analytics only, or PostHog (funnels, session
    replay, feature flags)?
  - *Sentry free tier + Cloudflare Web Analytics. Seller analytics use Analytics Engine.
    Revisit PostHog after launch.*
- **T17. Lint and format.** ESLint + Prettier (most complete Svelte support), or
  Biome / oxlint (much faster, but Svelte template support is partial)? *ESLint + Prettier.*
- **T18. CI/CD.** GitHub Actions running `wrangler deploy` (and `wrangler versions upload`
  for PR previews), or Cloudflare **Workers Builds** (the git integration with built-in
  previews)? *GitHub Actions; there are two Workers plus migrations to order correctly.*
- **T19. Subscriptions billing.**
  - Stripe Billing + Stripe Tax: you're responsible for SaaS sales tax in the states
    that tax it.
  - Or a merchant of record (Paddle / Lemon Squeezy) that handles the tax for you. On-site
    checkout later still needs Stripe Connect, so that would mean two payment vendors.
  - *Stripe for both.*
- **T20. Email templates.** Svelte components rendered to HTML on the server (one
  component system for everything), or MJML / React Email for better email-client
  compatibility? *Svelte components with a small set of tested, table-based layouts.*
- **T21. Admin tooling.** Build an in-app `/admin` area (reports queue, rescind
  disputes, bans, grant Pro), or manage things through the D1 console and scripts at first?
  *In-app `/admin`. Rescind disputes (D51) need a proper UI from day one.*

### Repo and process
- **T22. Repo conventions.** Conventional commits? PR-only to `main` with required CI?
  A license (proprietary vs source-available)? *Conventional commits, PRs with CI
  required, proprietary (no license file) for now.*
- **T23. Node version and runtime pinning.** Pin Node 24 LTS via `.nvmrc` and
  `packageManager` in `package.json`, and pin Workers `compatibility_date` with
  `nodejs_compat`? *Yes.*
